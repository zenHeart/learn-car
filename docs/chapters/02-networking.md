# 第 2 章 车载总线与通信协议

> 能力目标：car-networking — 根据带宽、实时性、可靠性与成本要求，在 CAN、LIN、FlexRay、车载以太网之间作出有依据的选型，并用报文示例说明 CAN 帧结构。

## 2.1 选型四问

选车载总线永远问四个问题：

1. **带宽需求**：控制信号（10 kbps 量级）还是摄像头原始流（≥1 Gbps）？
2. **实时性**：最差延迟必须 ≤1 ms 还是 ≤10 ms？
3. **可靠性**：节点出错时网络必须能容忍哪种程度的退化？
4. **成本**：每个节点是否需要独立收发器、晶振、屏蔽线？

这四个问题决定选 CAN、CAN FD、LIN、FlexRay 还是车载以太网，没有"最好"，只有"最匹配"。

## 2.2 CAN 与 CAN FD

CAN（Controller Area Network）由 Bosch 在 1986 年提出，ISO 11898-1 是其国际标准。经典 CAN 的带宽上限是 1 Mbps，最长 8 字节数据。CAN FD 把数据场扩展到 64 字节、带宽提升到 5 Mbps（仲裁段仍保持 1 Mbps 以兼容）。

CAN 帧由 7 段组成：

- 帧起始（SOF）；
- 仲裁场（11 位标准 ID 或 29 位扩展 ID + RTR）；
- 控制场（IDE + r0 + DLC）；
- 数据场（0–8 字节经典 / 0–64 字节 CAN FD）；
- CRC 场；
- ACK 场；
- 帧结束（EOF）。

仲裁段的优先级由 ID 数值决定：ID 越小优先级越高。当两个节点同时发"0x18DAF110"和"0x18FEF100"时，前者 ID 更小赢得总线，后者立即退让、下一个周期重试。这种"线与 + 仲裁"机制让 CAN 不需要中央调度就能保证高优先级报文的延迟上限——这是它成为汽车控制总线霸主三十年的根本原因。

CAN 总线是异步、多主、广播、半双工。任何节点都能发送，但同一时刻只有赢得仲裁的那个能继续，其余自动让出。物理层用差分双绞线，典型终端电阻 120 Ω 两端匹配。

## 2.3 LIN、FlexRay 与车载以太网

**LIN（Local Interconnect Network）** 是单线、≤19.2 kbps、主从结构的车身总线，主要用于对带宽不敏感但需要降低成本的节点：车窗马达、雨刮、空调风门、座椅调节。LIN 由一个主节点调度，从节点不需要仲裁器，所以单芯片 BOM 极低。

**FlexRay** 是 BMW 等厂商在 2000 年代为线控应用推出的高带宽总线，带宽 10 Mbps、双通道冗余、支持时间触发（TT）。它曾是 L2/L3 自动驾驶 ECU 互联的主流，但 2018 年以后被车载以太网逐步取代。

**车载以太网（Automotive Ethernet）** 是 IEEE 802.3 系列的汽车化改造：

- 100BASE-T1（IEEE 802.3bw）：单对双绞线 100 Mbps，物理层用 PAM-3 编码代替传统 MLT-3；
- 1000BASE-T1（IEEE 802.3bp）：单对 1 Gbps；
- 2.5G/5G/10GBASE-T1 系列：用于 ADAS 中央计算与区域控制器之间的高带宽骨干。

车载以太网之上承载多种协议：DoIP（诊断）、SOME/IP（面向服务的中间件）、TSN（时间敏感网络，IEEE 802.1Qbv 等）、AVB/AVBTP（音视频桥接）。中间件 SOME/IP 是 AUTOSAR Adaptive 的事实通信层，与 CAN 的"信号"模型不同，它采用"方法调用 + 事件订阅"，更接近面向服务架构（SOA）。

## 2.4 报文解析实例：CAN → J1939

以商用车 SAE J1939 协议为基础，把 29 位扩展 ID 拆解：

```
0x18DAF110
└─┬┘  └┬┘ └┬┘
  18   DA   F110
  │    │    │
  │    │    └─ 源地址 0x10（某个 ECU）
  │    └────── PGN 前缀（DA = PF 0xDA）
  └─────────── 优先级 0x6（6×2=18）
```

PF=0xDA（≥240）属于 PDU2 格式，PGN 直接等于 PF，即 PGN=0xDA00。低字节的 PS（0xF1）此时变成"组扩展"或保留。数据场以 SAE SPN（Suspect Parameter Number）解析，例如第一个字节 0x10 = 16 km/h 车速，第二字节 0x02 = 2% 油门开度，第三字节 0x03 = 3 bar 制动主缸压力。

学会把"16 进制"翻成"工程语义"是车载网络工程师的看家本领。

## 2.5 自检题

1. 为什么 CAN 仲裁机制能让高优先级报文的延迟有上界？
2. LIN 节省成本的根本机制是什么？
3. SOME/IP 与传统 CAN 信号的根本区别是什么？

## 2.6 报文解析练习

再给一段扩展 ID 帧：`0x0CF00400 08 52 6B 0F 00 00 00 00 00`。第一步拆仲裁：

```
0x0CF00400
优先级 0x03 (11 bit ID 的高 3 位 = 0x03 << 11)
PF  = 0xF0 (即 240)
PS  = 0x04
SA  = 0x00
```

PF=0xF0 ≥ 240 → PDU2 格式 → PGN = PF<<8 = 0xF000。数据场长度 8 字节：0x52 0x6B 0x0F 0x00 … 对应 SAE SPN 定义，这就是发动机转速/水温的常规轮询报文。

第二步换算物理量：0x6B 小端 16 bit = 0x0F6B = 3947，按分辨率 0.125 rpm/bit 得 493 rpm，与怠速 700 rpm 偏低→怀疑为冷车怠速或者已过 OBD-II 模拟器注入数据。识别工程异常值是车载网络调试的核心能力之一。

## 2.7 自检题答案

1. CAN 仲裁机制采用"显性 0 覆盖隐性 1"的线与机制。ID 越小显性位越靠前，因此赢得仲裁的高优先级报文持续占用总线，其余节点自动退让，最坏延迟由总线最大占用时间决定——这是 CAN 提供延迟上界保证的根本。
2. LIN 用单主多从架构，从节点不需要独立仲裁器与差分收发器，可以用普通 UART+稳压器+5 V 单线。BOM 成本约为 CAN 节点的 1/3–1/2。
3. SOME/IP 是"服务 + 方法 + 事件"，有服务端注册、客户端订阅、序列化/反序列化层；CAN 是"信号"模型，节点定时广播固定 ID，接收端按信号映射表解析。前者面向服务架构（SOA），后者面向实时控制。
